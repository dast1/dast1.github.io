These are notes toward an essay, not the essay. The question is the part I trust. I do not yet have an architecture I am willing to recommend, and I am not describing a product, a network, or a deployment anyone can buy.

The essay this becomes should sit after “Probabilistic Intelligence, Deterministic Control,” which separates generation, decision, and execution. It should set up a later one, on how personal, nearby, and centralized machines form a compute fabric. That later piece should wait until the governance question is sharper. Topology without a place for policy is just a diagram of where the weights sat.

## The question

If inference, memory, tools, and execution can each run on a personal device, on something nearby, at the edge, or in a centralized pool, where does policy enforcement live?

"Policy" here means the rule that permits or refuses an action: which principal, which data, which model, which side effect, which record. A prompt that asks the model to be careful is not that rule. A log written after the side effect is not that rule either. Enforcement is the ability to say no before the effect, and to show the no.

A system that answers in one place and acts in another can lose that ability without looking broken. The answer comes back. The action happens. Nobody can say which rule was consulted, or whether the context that justified the action was allowed to be in the room.

## Why local-versus-cloud is too small

The personal-computing note already argues for a bias toward the machine a person controls, with a path outward for work that is actually heavy. That bias does not answer governance once the path is real.

Three placements are not two. Work can stay on a device the person owns. It can move to something nearby: a machine in the same room, a box they operate, a network they have a reason to accept. It can go to a shared pool because the job is large, or because the tool they need does not exist anywhere else. "Nearby" is a trust and latency category. It is not a product name, and these notes do not propose to build one.

The governance problem starts when a single request crosses those placements. The model runs in one trust domain. The document it was allowed to see lives in another. The tool that can send, delete, or spend lives in a third. A policy written as if all three were one process will be a story the system tells, not a control it has.

## Where policy can live

I can see a few candidate sites. None of them is sufficient alone. This is a map, not a recommendation.

- **On the device that holds the sensitive context.** It can refuse to let the context leave. It cannot, by itself, restrain a tool running somewhere else.
- **At a gateway between placements.** It can see the request cross a boundary. It becomes a single place to compromise, and it sees only what the request was willing to show.
- **Inside the workflow that is the system of record.** This is the candidate I currently trust most for side effects. The workflow names the action. Ordinary code permits or refuses it. A remote model may propose. It may not authorize.
- **At the tool, again, as a second check.** The tool knows its own danger better than the planner does. A refund endpoint that believes the planner is a bad endpoint.
- **After the fact, as observation.** Necessary, and not enforcement. A log can support an audit. It cannot unsend the message.

Hypothesis: policy for a side effect has to be enforceable at the site of the side effect, before the effect, and it has to be able to refuse a proposal that arrived from a less trusted place. Everything else is input to that decision, or evidence after it. I have not tried to formalize this, and I do not want a slogan standing in for the formalization.

## Distributed inference

Once inference can move, "the model" is no longer a single dependency.

The weights that answered may not be the weights you pinned. They may be a quantized copy, a smaller stand-in, or a pool that routed you to whatever was free. A decision that was evaluated on one model and acted on under the assumption of another is a governance failure even if both models are competent. Provenance is part of the action, not metadata you attach when compliance asks.

Open: how much of the answer's identity has to travel with the answer. At least the model name, the version, and the placement. Probably the policy version that allowed that placement to see that context. I do not yet know the minimum record that would let a person reconstruct the decision a week later.

## Heterogeneous hardware

A policy that assumes one runtime will be wrong. Accelerators differ. Memory differs. Quantization changes behavior in ways a latency dashboard will not show. A model that is acceptable on one device can be a different statistical object on another, under the same name.

This is an engineering fact I am confident of in outline and not prepared to cite in detail. Before the essay is published it needs a source, or a smaller claim: same weights, different numeric format, do not assume the same error. The smaller claim may be enough. The essay should not borrow a hardware vendor's reliability story.

Failure domains follow the hardware. A personal device dies, sleeps, or leaves the network. A nearby machine is someone else's uptime even when you trust it. A centralized pool fails in correlated ways: an outage, a bad rollout, a region. The escalation path has to name which failures are independent and which take the policy down with them. If the policy engine lives only in the pool, a pool failure is also a control failure. That coupling should be an explicit choice.

## Privacy, residency, and what is allowed to move

Some context must not move. A document, a message, an unfinished argument, a record that is not allowed to leave a jurisdiction or a machine. The decision that needs that context is not therefore required to run in the same place as every tool.

A pattern worth testing: do the narrow decision beside the data, and send onward only the label, the confidence, and the identifier of a workflow. Not the document. The generative plane, if it still needs the document, either runs where the document is allowed to be, or it does not run.

Hypothesis, and only that: a lot of what currently looks like "the model needs the file" is a decision that needed a feature of the file. If that is true, distribution gets easier, because the sensitive object stays put and a small decision crosses the boundary. If it is false, and the open-ended reasoning genuinely needs the raw context, then that request is not a candidate for a remote generative call. Routing should be allowed to say so.

Data residency is the legal version of the same boundary. I am not going to fake a compliance analysis. The architectural point is prior to the statute: a system that cannot say where a context went cannot obey a rule about where it may go.

## Routing is a trust decision

Routing is already a product decision when it chooses a model: what good enough means, which failures are acceptable, whether the person can see the switch. Distribution adds a prior question. Which trust domain is allowed to see this context, and which placement is allowed to propose an action.

Cost and latency still matter. They are not the policy. A cheaper pool that is not allowed to hold the document is not a candidate, however good the price is. A local model that cannot do the work is not a virtue. The route is a record: placement, reason, what was allowed to travel, what was refused.

These notes do not assume a network I operate. They assume the person, or the organization, can name the placements they already have and the rules between them.

## Permissions

A remote model proposing an action is not authorization. The action set is local to a tool and a principal. The principal is a person or a service with a defined right, not "the agent."

The decision plane can answer "does this look like a refund request" and "how sure are we." The permission check answers "may this principal run this workflow." Collapsing those into one completion is the failure the previous essay is about, made worse by distance. Across a trust boundary, a probabilistic judgment and a deterministic permission have to be different messages. One of them is allowed to be unsure. The other is allowed to be no.

## Model provenance

A governed system can answer "what ran." Weights, version, who can change them, whether a silent alias moved underneath a threshold you fitted last month. If a threshold exists, the model identity is part of the threshold. An alias that tracks "latest" is a policy change you did not review.

I am stating this as a principle. I do not have a specific incident I am ready to cite. The essay should either find one that is public and fairly described, or stay at the principle and not gesture at a horror story.

## Observability

If the work is distributed, the record has to be joinable. Otherwise distribution is a way to lose the plot.

The record I would want, for one action: the placement of the model, the model version, the decision and its confidence, the policy version, the workflow, the principal, and the side effect. What context was in scope, named, not necessarily copied into the log. A copied document in an audit log is a second residency problem.

Open: who is allowed to see that record, and how long it lives. Observability that builds a shadow copy of private context has failed the policy it was meant to defend.

## Deterministic orchestration

The plan of record should be a workflow, not a trace reconstructed from completions. Across machines this matters more, because the trace will be partial. One placement saw the context. Another saw the tool. A third saw the person. None of them saw the whole story unless something that is not a model holds the story.

That something is ordinary orchestration. State machine, queue, workflow engine: I do not need to pick a product to insist on the role. The role is the ordered, inspectable, retryable account of what was supposed to happen. Models propose transitions. The orchestrator commits them, or refuses.

Hypothesis: once a repeated path crosses a trust boundary, leaving the path inside an agent loop is not just expensive. It is unauditable, because the path was never an object. This is the same migration as in the control essay — novel reasoning, then a pattern, then a workflow, then a narrow decision, then software — with the added constraint that the workflow is the only object all the placements can share.

## Failure and escalation

Escalation has to be a designed path, not a lower temperature.

When the decision is unsure, when two placements disagree, when a link is down, when a model version changed: the system needs a branch a person can find. Sometimes the branch is a more trusted placement. Sometimes it is a person. Sometimes it is a stop. A distributed system that "retries the agent" on uncertainty will retry the uncertainty.

Failure domains should be drawn before the outage. What still works if the personal device is offline. What still works if the pool is down. Which side effects are forbidden unless a named placement is reachable. A system that cannot act safely while degraded should refuse, and the refusal should be local enough to happen when the network is the thing that failed.

## What this essay must not become

- A design for a commercial fabric, a device, or a company.
- A claim that distribution is inevitable, or that centralization was a mistake. Centralized inference is the right placement for a lot of heavy work. The question is whether the control plane survived the trip.
- A survey of confidential computing, edge runtimes, or attestation. Those are relevant mechanisms. Naming them without a source, or without saying what problem each one actually solves, would be decoration. If the published essay uses them, each one needs a citation and a sentence about what it does not solve. Attestation can tell you what code ran. It does not choose the policy.
- A list of future essays. The only successor worth naming is the compute fabric: once there is a defensible place for policy, how should personal, nearby, and centralized compute be arranged as one system, with routing as a first-class record. That piece is "The AI Compute Fabric." It should not be written as a pitch. It should be written as a consequence of this question.
